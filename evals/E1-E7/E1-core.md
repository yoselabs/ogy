# E1 - task-loop factory core in spec-v3 (exercise, 2026-11-17)

Sources: spec-v3, tl-8bh9.8.7 plan, glossary (factory vocabulary as built), execution-terms (restart, repeat, hold).
Scope: task -> step (plan, implement, checks) -> attempt; slots, reservations, hold, repeat limit, crash/resume.
Land, publish, setup runs, labels, tracker claim leases are only touched where they interact.

## 2. Edge cases the description exposes
1. Repeat vs re-run vs rework. Three limits of 3 (repeat per agent step, re-run of checks after main_moved, setup failure 2). Sources have no single "rework limit"; entries `repeat-cap`, `max-rerun`, `setup-fail-limit` all name a different counter. A checks failure never triggers implement rework here (open: sources say a failed checks attempt is only re-run; return to implement after genuine failure is not stated).
2. hold-task vs repeat. `repeat` exhausted calls `hold-task`, which waits for `attempt.release`; but a hold's abandon happens "when the slot allows". A setup process still alive (`held:setup_running`) keeps the slot reserved, so the task is held yet the slot cannot be reused: entries `hold`, `reservation`, `slot` disagree for a while.
3. Crash between launch and acknowledgement. `dispatch` records B, then phase `dispatching`; if the factory dies before `register`, `live-execution` is unknown. `no-competitor-launch` needs "alive" but the tool cannot evaluate agent-harness liveness (environment, nondeterministic). Open: spec has no unknown/three-valued state.
4. Claim lease vs resume. The tracker claim lapses ~5-15 min after a step ends; a restart longer than that finds the task open in the tracker while `attempt` is unfinished in factory.db. `task.claimed` has two owners (tracker and DB); `--retake-lapsed` logic is not in any entry.
5. Crash is not an attempt, but `relaunch` of entry on the same attempt renews the deadline. `attempt.deadline` is both a timeout (`?timeout` re-arms on every entry) and a stored fact renewed once per reboot; the spec timeout re-arm would re-arm on every relaunch, not "once per reboot".
6. Hold and abandon: abandon returns the claim and makes the task `ready`, hold removes approval label so it is not re-admitted. Two tracker writes plus one DB row (`hold` phases recorded/labelled/commented). A crash after `record` but before `label` leaves `task.held` true in DB and approval label still on: `round` may re-admit unless `held-blocks-admission` reads DB. Order of `round.settle` (re-takes held tasks "taken again") vs `hold-task` is a race on the same task.
7. Parallel tasks. Two tasks admitted in one round: `max-new` limits fresh tasks, but advance (next step of an existing task) is not counted. `slot-free` count is read once per task in `for_each`; the second admission sees the reservation of the first only if the loop is sequential (open).
8. Slot reserved vs locked. Release parks the slot (a Git write under custody) while a verify on the same slot runs custody too; "never waited for" gives `slot_busy` refusal, an end not modelled by `release`.
9. Land pending a second slot. A land candidate and a checks attempt each hold a slot for the same task; `reservation` unique on attempt, so one task may own two reservations. `one-reservation-per-slot` holds, but "one slot per task" is false and nothing states which.
10. Session shared across attempts; fresh-session default after completed step (feedback re-entry) vs resume same session after restart. `session` lifecycle depends on why the new attempt happened (reason is a single text field `repeat_reason`).

## 3. Slippery slope
- Timers crossing: attempt deadline (minutes), tracker lease renew (100 s), reclaim grace (10 m), hold comment lease (120 s), round interval. Each is a `?timeout` or value on different entities; only the deadline is a workflow timeout. Crossing cases (lease lapses while deadline runs; comment lease expires during crash) need a combined Quint run, and the lint cannot say which timer wins.
- Many conditions: `verify.judge` cases on disposition x effect x verdict x branch_moved x environment; `Next` words (start, wait, land, hold, on_hold, stuck:*) are a derived function of 6+ facts. As a case table it is complete and ordered but the table has about 12 rows across `then:` targets; adding a stuck word touches round, resume, hold-reason and interface.
- One entity changed by many workflows: `task` is written by admit, hold-task, unhold, abandon, land, advance and the tracker itself (external). `attempt` by dispatch, verify, repeat, resume, stop, release. Conflict clauses per step multiply; `?conflict.then` has no way to say "re-read tracker".
- Two counters with the same shape (repeats, reruns, setup_failed, relaunches) invite a generic "counter with limit and exhausted reason" that the spec does not have; each is a copy of the same rule.
- Terminal vs reusable: attempt `released` is terminal, but slot reuse and `reservation` delete are effects not transitions; lifecycle of reservation is existence, not state.

## 4. Misfits
- M1 Split ownership: task state lives in the tracker (external) and factory.db at once. `entity` has one lifecycle; no way to mark an attribute as "read from external, cached, may disagree". Used `task.held` + external events, awkward.
- M2 Process/OS liveness: `pid_identity`, boot id, process group alive are environment facts with unknown result; spec has externals with events but no query-with-unknown nor "stop proof".
- M3 Atomicity across stores: admission is "one transaction" reserving a slot, creating an attempt and taking a tracker claim. Spec says a row's effects are atomic but one effect is `tell external`; no compensation ("return the claim on refusal").
- M4 Crash and resume as workflow: trigger `event: transition/factory.restart` needs the factory as entity with a transition; the factory is not an actor, the clock is not an actor, and restart is neither. Modelled as pseudo-transition.
- M5 Intact vs discarded factory.db: "discard permits reevaluation" is a different start state of the world, not a step; no construct for initial-state variants.
- M6 Deadline renewal "once per reboot": needs "once per" memory; counter reset on external event not expressible besides an extra counter attribute.
- M7 Parallelism: nothing for "n workflows concurrently, bounded by a resource set". `for_each` is sequential in meaning; the slot pool is a set member count, not a semaphore.
- M8 Evidence files and logs: "control state never read from logs" is a negative statement about readers; only a holds rule with prose, no check.
- M9 Executions: attempt has at most one execution with stored facts (usage, exit); modelled as no entity because attempt attrs were enough, so "one execution never belongs to two attempts" has no check expression.
- M10 Question/answer: a human question is an `?open`, a hold and an `ask` workflow at once; `?open` is for spec questions, not runtime ones, so `ask-owner` is a normal workflow with a `wait until`.

## 5. Unused / over-engineered
Unused: quality beyond one entry, `adds` rules, `?tags` (used once as scope), `?each` choice, `{add|remove}` list effects, `{clear}`, `dependency` (only bd), `operation`, `constant` as meaningful (a one-liner), `trigger: {after, since}` (the hold comment lease and lease lapse would fit, but I put them as values), `money`, `date`, `?for` choices, FEEL ranges, receipts block (proof/built/covers: no proof exists to attach in this description).
Over-engineered for this core: receipts/fingerprint details in a description exercise; two ways to say a limit (`max:` on attr and a `guard` rule) overlap; `?wait {for}` vs `?timeout`; separate `derived` plus `holds check` for one fact; layer ceremony (business/technical) when nearly every core fact is technical and no owner-business value was stated beyond the three limits.
