# Harmony review of the software ontology, 2026-11-19

Scope: `src/ogy/ontologies/software` (32 kinds), the engine that reads it (`src/ogy`), and three knowledge bases written
with it: ogy's own (`docs/kb`, 623 entries), `tests/fixtures/tool-library` (86 entries, every kind) and
`tests/fixtures/taskloop-fit` (the most realistic flows). Nothing was changed; no entry was written. Every number below
was measured on commit `f57678a` with read-only scripts over `ogy.snapshot`.

Verdict in one paragraph. The flow core (workflow, step, rows, ends) and the lifecycle core (entity, state, transition)
are sound and well checked. Around them the model has four soft spots: the rule kind is an island, the layer split is not
enforced, three kinds answer the same question "what if a condition does not hold", and the engine still knows the
software ontology by name in about twenty places. Fixing those four removes 3 kinds, about 12 fields and most of the
guessing an agent does today.

## 1. Method and criteria

How harmony is judged here. Seven criteria, each with the measurement that decides it, so a finding is a number or a
quoted entry, never taste.

| # | Criterion | How it is measured |
|---|---|---|
| C1 | One concept, one kind. For each pair of kinds that could be confused there is one test that separates them. | State the test; then read real entries and count the ones that break it. |
| C2 | One owner per fact. No fact is written in two entries, or in two fields of one entry. | Look for pairs of texts that must be kept equal by hand or by a check. |
| C3 | One meaning per name. A field name or a link verb means one thing on every kind; a link has one direction. | Table of every field name across kinds; note each second meaning. |
| C4 | Connected and read. Every kind is reachable by links; every field has a reader that would notice a wrong value. | `ogy kinds --readers`; per kind, the share of entries with no link in or out; fields never used in a real knowledge base. |
| C5 | No guessing (principle intuitive-for-ai). An agent with the kinds, the glossary and one entry can place a new fact in exactly one way. | Model a common web application by hand; every place with two valid ways is a friction. |
| C6 | Economy. Nothing can be removed without a check losing something. | For each kind and field: which check, printer or work derivation fails if it is deleted. |
| C7 | The engine is generic. Python names no kind, field, layer, tag or word of the software ontology. | Grep the engine for literals; list each as "move to YAML". |

Two guards on the method itself:

- A model is judged by its entries, not by its kind files. A kind that is clean on paper and misused in 60 of 65 real
  entries is not clean. So every finding cites real entries.
- "The fingerprint reads it" is not accepted as a reader for C4. Every field that is not a note enters the fingerprint
  automatically, so by that standard no field could ever fail. A reader is a check, a printer or a link walk.

The running example is a web application: sign-in, password reset, an admin user list, a nightly cleanup, a breach
detector and an orders page. Section 3 gives one line of it per finding; the friction log is at the end of section 2.

## 3. Findings, ranked by how much harmony they buy

Marks: delete, merge, rename, restructure, move-to-YAML, reword.

### 1. The rule kind is an island (restructure)

What is wrong. A rule should be "what must stay true; a test can catch it broken; the entries held to it name it with
`by`". In ogy's own knowledge base none of that holds, for three causes that feed each other.

- Decisions mint rules. 56 of 66 decisions do nothing but set the `says` of one rule, and 60 of 65 rules exist only as
  that mirror. The chosen option's label and the rule's sentence say the same thing twice (C2). Rewording the rule then
  needs a new option and a new answer: `rule-linked-by-follower` has 6 options and 4 answers for one sentence.
- Many of these are not rules by the owner's own test. `review-delegation`, `structural-delegation` and (fixture)
  `agent-decides-fee-details` are delegations, which the README already defines as "the owner's answer to a decision".
  `examples-before-kinds` is a plan. `area-is-the-word` is a term's `avoid`. `ogy-is-one-package-for-now` is a choice. No
  test can catch any of them broken.
- The real rules cannot be linked. `by` is declared on 8 kinds (attr, case, choice, entity, external, guard, timeout,
  workflow). The rules of ogy's kb are about commands, operations and storage, and those kinds take no `by`. So
  `remove-needs-a-reason` cannot be named by the command `remove`. Result: 0 `by` links in 623 entries; `ogy impact` of
  any rule is empty.
- A rule cannot name the number it is about. The guidance says "a decided number is a value the rule names", and the rule
  kind has one field, `says`. Fixture: "A member holds at most max-loans tools at once" names the value in text only,
  which the principle rigid-where-checked forbids ("text that names another entry makes that part a link"). Changing the
  value from 3 to 5 makes no rule's proof stale.

Evidence. Table in section 2; `docs/kb/software/ontology/decision/trigger-computed.yml` and its mirror
`rule/workflow-start-is-computed.yml`; `kinds/rule.yml`; scratch test: a decision whose options have `sets: {}` passes
`ogy check` and shows as a normal question in `ogy review`, so the engine already allows a decision that stands alone.

Proposal.
1. A decision stands alone when its outcome changes no entry. Its record is the chosen option. `option.sets` stops being
   required; the decision's `about` and guidance say so. A rule is written only when a test could catch it broken.
2. `by` becomes a common field (with `because`): any entry may be held to a rule. Rows keep it in their build hash as now;
   everywhere else it is a note.
3. `rule` gains `reads` (links to value, set, config_key), inside its build hash, so a changed number makes the rule's
   proof work again.
4. Sort the 65 rules once: a real invariant stays and gets a holder or a proof; a delegation, plan or naming choice is
   removed with its decision as the reason.

Without it. The kind with the most entries after decision carries no checks, no proofs and no links; "rule" quietly
means "note", and the distinction principle, decision, rule that the owner settled exists only in the glossary.

Cost. Small in code (one common field, one link field, one requirement relaxed). One review round to sort the rules.

Web example. "An account locks after max-failed-attempts wrong passwords": the rule reads the value, the case `lock` is
held to it with `by`, and the choice of 5 attempts is a decision that sets the value, not a second rule.

### 2. The layer split is stated and not enforced (restructure)

What is wrong. Principle layers-split-business-from-technical says a business fact lives in product and a build fact in
software. Nothing checks which way links cross. The kind files invite the wrong way: a product workflow's `when`, `effect`
and `by` may name `external` and `config_key`, kinds that live only in software.

Evidence. taskloop-fit: 35 links from product to software in one workflow (`product/land/workflow/land`): 13 effects on
transitions of a software entity, 9 conditions reading software externals, 5 reading software states, 3 held to software
rules. Its steps (`squash`, `push-answer`, `again`) are the code's control flow, each with a `src` to a Python function.
That is the "all rigid" failure the guidance warns of, placed in the product layer. Tool-library: `notify` case `ok` reads
`software/lending/external/mailer`. ogy's kb: `init-repository` writes to `software/.../external/git`.

Proposal. `ontology.yml` declares the direction: layers are ordered, and a link goes within a layer or from a later
layer to an earlier one (software names product; product never names software). One generic check, `bad-layer-link`.
In product, the outside party is an actor (who we tell); in software, the operation `uses` the external. Kinds usable in
product drop `external` and `config_key` from their link targets only through this check, not by editing every list.

Without it. The product layer cannot be read by the owner without software knowledge, a store or vendor change edits
product entries, and "what the business decided" is not separable from "how it is built", which is the reason the layers
exist.

Cost. One check and one line in `ontology.yml`; taskloop-fit's land workflow moves to software or is cut to its
business steps; 6 links elsewhere (3 of them a product decision answered under a software delegation).

Web example. Product: "the reset mail could not be sent" is a case with text and an effect `tell` the member. Software:
operation `send-reset-mail` uses the external `mailer`. Swapping the mail vendor touches software only.

### 3. Three kinds answer "what if the condition does not hold" (merge)

What is wrong. A guard, a case and a choice's `when` overlap, and the step's actor is a fourth home for "who may".

| Question | Homes today |
|---|---|
| Who may act here | step.actor; guard (`harm: who-is-allowed`); choice.when (`harm: who-is-allowed`); a rule |
| Refuse when a fact does not hold | guard `else`; a case that goes to a failure end |
| Fewer choices under a fact | choice.when; a case before the step |

The test the guidance gives ("a guard refuses entry, a case branches inside a step") does not separate them: a guard on a
system step is exactly a case with the lowest `order` and the negated condition. Real entries show it:
`review-and-reply/step/apply` has the case `changed -> refused` and, in another file, the guard
`all-round-names-its-cards -> refused` on the same step. Same construct, two kinds, opposite polarity of `when` (guard:
must hold; case: if it holds, take this path).

More evidence. All 9 guards in the three knowledge bases sit on a step, none on a workflow, and 5 of 9 have a text-only
`when`. Every guard's `says` restates its `when.text` (two texts for one condition inside one entry, C2).
`guard.on -> workflow` is declared and broken: in a scratch copy of the fixture, an end reached only by a workflow-level
guard is reported `end-unreached`, because `flowcheck.graph` only adds guards found on steps.

Proposal. Delete the kind `guard`. One home per question:
- who may act here at all: the step's actor (a different actor is the variation test the actor kind already teaches);
- the same actor sees fewer choices: `choice.when`;
- the product refuses or branches on a fact: a case; a refusal is a case whose `then` is a failure end.

`Flow` loses `guard`, `guarded` and `denied`.

Without it. An agent picks by habit; the harm tag who-is-allowed is on two of the four homes; reviews rank a refusal
written as a guard above the same refusal written as a case.

Cost. 9 entries become cases. What is lost: a software entry adding a refusal to a product step without editing it
(2 uses). Both of those refusals have a product end already, so the product knows them; see owner decision 3.

Web example. "Only an admin opens the user list": the step's actor is `admin`. "A locked account cannot sign in": case
`locked`, order 1, then end `refused`. No guard in either.

### 4. The engine knows the software ontology by name (move-to-YAML)

What is wrong. The owner's goal is to change only YAML. Today about twenty facts of the ontology live in Python, so a
rename in a kind file either breaks silently or has no effect.

Evidence (file, what is hard-coded):

| Where | Hard-coded | Belongs |
|---|---|---|
| `kinds.py` COMMON_FIELDS | title, src, because, proof, agreed and their types | `ontology.yml` `common:` |
| `kinds.py` Harm | the five harm tags, their order, and that `structure` gets its own card (`render.py`, `rounds.py`) | `ontology.yml` `harms:` (ordered; `alone: true`) |
| `kinds.py` Flow, Settling | every default name (`step`, `choice`, `otherwise`, `sets`, `chose`...). `workflow.yml` says `flow: {}` and `decision.yml` says `settling: {}`, so the names are Python's | written out in the two kind files; no defaults |
| `flowcheck.py` | the step shapes (actor step: choices and nothing else; system step: cases or one `then`; one `otherwise`) as Python sentences. Decision graph-rules-declared says they belong in kind files | `requires` in `step.yml` (needs `needs_part`, `if_unset`, `forbids`); reach, cover and offered stay as named generic checks |
| `terms.py` | kind `term`, fields `word`, `says`, `avoid`, 15 words, the list of text fields | a `glossary:` role on the kind; text fields from field types |
| `constitution.py` | kind `principle`, field `why` | a `printed_first:` role on the kind |
| `status.py`, `find.py`, `removal.py`, `pages.py`, `reply.py`, `diagram.py` | "the sentence is `says`, else `question`, else `label`, else `word`"; `address.kind == "term"` | each kind names its `sentence:` field |
| `reply.py` `_reopen` | builds a decision by literal names (`question`, `options`, `label`, `sets`, `guess`, `chose`, `why`), bypassing Settling | through Settling's names |
| `settle.py`, `writes.py`, `fieldtypes.py` | the key `answers`; the words `human` and `ai`; the shape of `agreed` | from the kind (`key`, enum members); `agreed` declared as a part |
| `evidence.py`, `evidencecheck.py` | schemes `code:` and `doc:`; `.py` only; proof is `<path>.py::<function>` | `ontology.yml` or `ogy.yml` `evidence:` |
| `cli.py` WHERE and `answer.yml` schemes | the same list twice | the kind file only |
| `kindlint.py` STORED_STATE, SENTENCE_NAMES | 29 banned field names from past versions; "the sentence is `says`" | `ontology.yml` `reserved:`, or delete |
| `init.py`, `layout.py` | `product/shared`, `constitution/principles.yml`, the shared area's sentence, the default ontology, the AGENTS block that names kinds and fields | `starts.yml` and a block template in the ontology folder |
| `readers.py` NAMED | a hand-kept map of which check reads which field | derived from the roles above |
| `ontology.yml` | holds only `layers` | layers and their order, common fields, harms, evidence, reserved names |

Proposal. Move each row. The acceptance test is a second, tiny ontology in `tests/` in which every kind, field, layer
and tag has another name, and the whole suite passes on it. Until that test exists, "generic engine" is a hope.

Without it. Every later proposal in this review that renames or merges a kind needs a Python edit, and the next ontology
cannot be written at all.

Cost. The largest item here: touches about 15 modules, changes no behaviour. It is also what makes everything after it
cheap.

Web example. A team that says "screen" and "endpoint" renames two kinds in YAML; today `Flow.servers` in Python still
says `("view", "command")`.

### 5. View and command are one kind (merge)

What is wrong. Both "serve actor steps" and "offer choices". Same links, same fingerprint paths, and `Flow.servers`
treats them as one. No check, printer or work derivation tells them apart; the only difference is `invoked_as`, which
only the fingerprint reads. By rigid-where-checked a distinction no check reads is text. The fixture already blurs it: a
view named `leave-button` (a button, not "a screen") next to a command that serves the same step.

Evidence. `kinds/view.yml`, `kinds/command.yml`; `kinds --readers`; ogy's kb has 21 commands and no view, the fixture 2
views and 1 command on one step.

Proposal. One kind, `interface`: how an actor reaches a step. Fields `says`, `serves`, `offers`, and `as` (optional: the
exact command line, route or screen name). The owner did the same for persona, role and user: one `actor`.

Without it. An agent building an API endpoint and a form for one step chooses between two kinds with nothing to guide it,
and a product with both a web page and a CLI for the same step doubles its software entries for no check's benefit.

Cost. A kind merge needs the one-off kind rename path in `migrate` (README: "a renamed kind key ... needs a one-off
migration"); 25 entries.

Web example. `interface/sign-in-form` and `interface/post-session` both serve step `enter`; the second offers only the
choice `submit`.

### 6. A term repeats an entry, and term is linked to nothing (restructure)

What is wrong. Decision terms-are-types says the glossary holds types, not instances. An entity, an actor and a state are
types too, and each has its own `says`. So the same definition is written twice, and `duplicate-says` cannot see it
(it compares one kind in one area).

Evidence. Fixture: term `loan` "One tool lent to a member until it comes back; not a reservation" and entity `loan` "One
tool lent to one member until it comes back." Term `member` literally says "the actor product/lending/actor/member" in
text. ogy's kb: terms `decision`, `entry`, `review round` and `answer` have entities, commands or transitions of the same
name. Term `area` says "not a kind"; `area` has been a kind since decision area-entry. Term is the only top kind with no
link field: 32 of 32 terms are isolated.

Proposal. A term either defines a word no entry defines (says), or names the entry that defines it (`names`, a link to
any kind): exactly one of `says` and `names`. The glossary prints the named entry's sentence. A term whose word equals
the id or title of an entity, actor, state or set in its layer, without `names`, is `word-clash`. `avoid` stays where it
is: it is the part of a term nothing else can hold.

Without it. Two sentences per concept drift; an agent adding entity `order` has to guess whether a term is wanted too.

Cost. One link field, one requirement, one clash rule; about 10 terms change.

Web example. Term `account` names `product/auth/entity/account` and carries `avoid: [profile, user record]`; it has no
sentence of its own.

### 7. The decision's parts carry four redundancies (delete, merge)

What is wrong and evidence, one by one.

- `heard` is a kind with one text field, `said`. It is a field of the guess dressed as a kind. With `guess` and `timeout`
  it is one of three users of the engine's `holds: one` mode.
- `guess.sets` (a guess with no option) is used 0 times in ogy's kb and exists so a decision can have no options. It
  forces `exactly_one_of`, a second shape for every reader of a guess, and the rename history `value -> sets`. If the
  guess is always an option (an open question has at least the one option the AI would build), the field and the rule go.
- `answer.from` repeats `answer.delegated`. Check D10 enforces: `from: ai` if and only if `delegated` is set. One fact,
  two fields (C2).
- `agreed.from` can only be `human` (`fieldtypes.agreed_problems` refuses anything else). A field with one legal value.
- `said` means two things (C3). On an answer, a guess and an agreement it is the paraphrase of what a person said. In
  `removed.yml` it is the removed entry's own sentence (its `says`).
- `option.label` holds full sentences (up to 30 words in real decisions) and is "the sentence" of an option, while every
  other kind's sentence is `says`. `choice.label` is a real label (button text). One name, two jobs.

Proposal. `heard` becomes a text field of `guess`; `guess.sets` is dropped; `answer.from` and `agreed.from` are dropped
(who answered is computed from `delegated`); the ledger's `said` is renamed `says`; `option.label` is renamed `says`.

Without it. Nothing breaks; an agent keeps learning six special cases that no check needs.

Cost. `Settling` loses three names; `migrate` renames; the four optionless decisions of the two fixtures gain one option each.

Web example. "Lock after how many attempts?" has options 3, 5, 10; the guess chooses 5, `why` "common practice",
`heard` "you said like the bank does".

### 8. The why-chain has three verbs and no check (rename, restructure)

What is wrong. Goal, capability and workflow are tied by three link names for one relation ("exists for"):
`goal.for -> actor`, `capability.serves -> goal`, `workflow.realizes -> capability`. `serves` also means something else
on view and command ("is the surface of a step") (C3). None of the three links is required and no check reads the chain.

Evidence. ogy's kb: 6 of 14 capabilities serve no goal, 7 of 14 are realized by no workflow, 4 of 11 workflows realize
nothing. `capability` carries `harm: who-is-allowed`, which describes nothing about a capability.

Proposal. One verb, `for`, up the chain: workflow `for` capability, capability `for` goal, goal `for` actor. `for` is
required on goal and capability. A capability that no workflow is `for` is reported as work left, not as an error (it
was decided before it was built). Drop the harm tag from capability.

Without it. The why-chain decays exactly as measured; `impact` from a goal reaches half the product.

Cost. Two renames through `migrate`, two `required`, 6 capabilities need a goal.

Web example. Workflow `password-reset` for capability `recover-access` for goal `nobody-is-locked-out` for actor
`member`.

### 9. Effects say one thing in two ways, three times (delete, reword)

What is wrong.
- `create` and a transition without `from`. The transition kind says "without `from` the entity is created in `to`". The
  fixture writes both on one row (`create loan` and `transition start`).
- `count` and `write`. `count` names "the attribute it counts", and `attr.type` has `counter`. No check ties them: a
  `count` effect may name a text attribute, and a counter may be written.
- `tell` and `write` on an external. ogy's kb writes to Git with `write`; taskloop-fit pushes to origin with `tell`. Both
  mean "we change something outside".
- The `do` list is where harm lives in practice (delete is irreversible, tell goes outside, money moves), and harm cannot
  be declared on an enum member. So the tags `moves-money` and `irreversible` exist in Python and no kind uses them.

Proposal. Verbs: `create`, `delete`, `write`, `transition`, `tell`. Drop `count` and the attribute type `counter` (a
count is a write to a number). An entity with a lifecycle is created by its first transition; `create` is for an entity
without states. On an external the one verb is `tell`; `write` names only our own entities and attributes. Let an enum
member declare `harm` (`delete: irreversible`, `tell: tells-outside`), so the review ranks the row that deletes.

Without it. Two agents write the same behaviour differently, and diffs and impact disagree.

Cost. One enum member, one attribute type, 4 requirement lines, a small engine change for member harm.

Web example. Nightly cleanup: `delete` on entity `session` ranks as irreversible in review; the failed sign-in is
`write` on `account/attr/failed-attempts`.

### 10. Flow frictions: where an edge lives, the magic key, acting then branching, reads (restructure, reword)

What is wrong.
- A step's exit lives in two places: on a row (`then` of a choice, case or timeout) or on the step itself (`then`, used
  twice in ogy's kb and the tool library). A step cannot hold an effect, so "do one thing and go on" is written as
  `cases: {otherwise: {effects, then}}` (taskloop-fit `push`, `close`), and the plain `then` is left for steps that do
  nothing.
- `otherwise` is a meaning carried by an id. It is declared, yet it is the only place where a key changes a check.
- Acting and branching. A case's `when` is read as a condition before the step acts (`full: the member holds max-loans`)
  and as the outcome after it acts (`ok: the mailer accepted the message`). taskloop-fit therefore splits `push` and
  `push-answer` into two steps; the fixture keeps one. Both pass. An agent has to guess.
- In a calling step a case selects by `covers_ends`, not by `when`, and may still be keyed `otherwise` with an `order`
  (fixture `remind`), though no catch-all counts there.
- A read leaves no trace. Effects model changes only; a view has no link to what it shows. Changing entity `order` does
  not reach the orders page in `impact`. Read-only pages need a workflow with a ceremonial `leave` end.
- 13 of 14 actor steps in ogy's kb have one choice, whose label repeats the step ("Check", "Reply").

Proposal.
1. Edges live only on rows: drop `step.then`; a system step always has cases; the plain step is the one `otherwise`
   case. One shape fewer, and effects always have a home.
2. Say the reading of `when` once, in the step and case guidance: "`says` is what the product tries at this step; a
   case's `when` is what it found; the effects are those of the case taken". Then one step is right, two are noise.
3. Rename `covers_ends` to `ends`; in a calling step the key `otherwise` and `order` are refused.
4. Add `step.shows` (links to entity and attr): what the actor is shown at this step. Read by links and impact; with
   member harm from finding 9 it can carry who-sees-what.
5. Leave single-choice steps as they are; the choice is the act and the row that carries proof.

Without it. The best-checked part of the model keeps three small guessing games; the commonest thing a web application
does (show a list) stays outside the graph.

Cost. `Flow` loses one name; 3 entries change shape; one new link field with a reader.

Web example. Step `browse-orders` (actor member) shows `order` and `order/attr/total`; changing the attribute `total`
reaches the orders page in `ogy impact`.

### 11. `because` has two meanings and any target (reword)

What is wrong. The kind files and the AGENTS block say `because` "cites a principle or a decision as the reason". The
glossary term says "links to the entries a sentence was concluded from; they must reach a src". The evidence check uses
the second and accepts the first: a principle needs no evidence, so citing a value grounds any factual claim. The field
links to `any` kind.

Evidence. `kinds.COMMON_FIELDS`; `evidencecheck._grounded`; term `because` in `product/shared/glossary.yml`; used 5 times
in all (principle 3, decision 1, rule 1). A `because` to the decision that already sets the entry repeats a computed
fact (`show` prints "Decided in").

Proposal. One meaning: the reason, as a link, to a principle, a decision or a rule. Narrow the target list. Evidence is
`src`, a settling decision or the owner's yes; a `because` grounds an entry only through what it cites. Reword the term.

Without it. "Why" (a value) and "where from" (a source) stay mixed, and an unsupported sentence passes `no-evidence` by
citing a principle.

Cost. One line in the common fields, one term, a look at 5 entries.

Web example. Rule `passwords-are-never-stored-plain` because principle `members-data-is-theirs`; its evidence is still a
`src` or the owner's yes.

### 12. Fields no check would miss; the principle's loophole (delete, reword)

What is wrong. `kinds --readers` reports one field read by nothing and five read only by the fingerprint. The real list
is longer once the fingerprint is not counted as a reader (section 1).

| Field | Read by | Proposal |
|---|---|---|
| area.distinct | nothing. Term dropped the same field for compression; area kept it. Its real values name other areas in text ("asking the owner: review") | fold into `says`; the areas named become a link field `near` so a renamed area follows |
| actor.nature | fingerprint only. Rule `who-may-say-yes` says "a second human actor is a finding"; no code reads `nature`, and the fixture has two human actors | give it the check it was made for, or reword the rule |
| end.result | fingerprint only | a reader: review ranks a changed failure end; or keep as is |
| command.invoked_as, config_key.name | fingerprint only | keep; the proof test is their real reader |
| set.members | fingerprint only; members cannot be named by a `when` | keep |
| attr.type | 10 members; only `one` is read (it needs `of`). It mixes what is held (text, number...) with how many (`one`, `list`), so a list of numbers cannot be said | `type` is what is held; a flag `many`; `of` for a link |
| harm tags moves-money, irreversible | declared in Python, used by no kind | finding 9 |

Also reword the principle or the report: as written ("a check, work left or impact reads"), every field passes because
work left reads every fingerprint.

Without it. The readers report says "all fine" while a wrong `nature` or `result` would never be noticed.

Cost. Small; each row is one line in a kind file.

Web example. Area `auth` says what it covers and links `near: [admin]`; renaming `admin` to `back-office` follows.

### 13. What makes work stale is picked by hand (restructure)

What is wrong. Which link carries a dependency into the build hash is written per kind in a path language:
`[by, "=@fingerprint"]`, `[serves, /choice, "=@id"]`, `["<-by", "=pin"]`, `[after, "=is"]`. Five kinds, five spellings,
and gaps: a case that reads a value in `when` is not stale when the value changes, though a timeout `after` the same
value is; `attr.max` is not in the entity's hash.

Evidence. `fingerprint.also` and `reached` in case, choice, timeout, command, view, operation, entity, rule;
`snapshot._along`.

Proposal. A link field says how it counts, in one place: `hash: none` (a note), `link` (the address, today's default) or
`target` (the target's content: a changed target makes this entry work). `after`, `max`, `reads` of a `when`, `binds`,
`uses`, `performs` and `by` on rows are `target`. The path language stays for the two reverse cases.

Without it. Adding a link field means remembering a second edit in a syntax the agent cannot guess (C5).

Cost. Medium: the build hash changes once for every entry, which is acceptable while nothing has a proof.

Web example. Raising `max-failed-attempts` makes the case `lock` and the rule that reads the value work again.

### 14. Thirteen kinds need a proof; the glossary says two (reword, delete)

What is wrong. Term `proof`: "a test showing a rule or value holds in code". `needs_proof` is set on 13 kinds: case,
choice, command, config_key, deviation, entity, guard, operation, rule, step, timeout, value, view. One button press
asks for a proof of the step, the choice, the view, the operation, the case behind it and the rule. ogy's kb: 172
entries of work left, 0 proofs.

Proposal. Say what "built" means per group and trim: a row (choice, case, timeout) is proved by a behaviour test; a rule
by an invariant test; operation, interface, config key, deviation and entity by a test of that code; a value by the test
that uses it. A step has no behaviour of its own once edges live on rows (finding 10): drop `needs_proof` there. Reword
the term.

Without it. Work left is a number nobody can drive to zero, so it stops meaning anything.

Cost. One flag, one term.

Web example. Sign-in: tests prove the rows `submit`, `locked`, `wrong`; the step `verify` asks for nothing more.

### 15. Storage leaks into meaning (restructure)

What is wrong. Principle storage-is-a-projection: "no meaning and no address depends on" how an entry is stored. Kind
files mix three things: what a kind is part of (meaning), how its file is laid out (`shape: entity|list|single`, `file`),
and whether a part has an address (`holds: list` items have none). So an effect and an answer cannot be linked, proved or
agreed on their own, because of how they are stored. `single` and `every_area` exist for one kind, area.

Proposal. Keep `part_of` in the kind (meaning). Move `shape` and `file` to a `layout:` block in `ontology.yml`. State
honestly in the principle, or fix, that list items have no address. Low priority: nothing is wrong in entries today.

Cost. Medium, mostly loader. Do it with finding 4 or not at all.

Web example. Moving values from one `values.yml` to a file per value would change one line of layout and no kind.

### 16. Names (rename)

| Now | Problem | Proposal |
|---|---|---|
| `config_key` | the only two-word kind; three spellings (`config_key`, `config-keys.yml`, "setting" in its own `about`) | `setting` |
| `external` | an adjective; reads as "any outside system", which includes callers that are actors | `dependency` |
| `value` | three senses: a decided number, a field's value in `sets`, and "a principle is a value" | `quantity` (a number with a unit) |
| `set` | next to the field `sets` and the file `sets.yml` | `enum`, or keep |
| `attr` | the only abbreviated kind | `attribute`, or keep for short addresses |
| `on` | guard: where it stands; effect: what it changes; rule: dropped | single meaning once guard goes (finding 3) |
| `from` | transition: the states left; answer and agreed: who | single meaning once finding 7 lands |
| `when` | select a path (case), show a choice (choice), must hold (guard), circumstances (deviation) | three after finding 3; say each in its field comment |

Cost. Each is a `migrate` rename; kind renames need the one-off kind path. Worth doing in one batch or not at all.

Web example. `software/auth/setting/session-ttl` binds `product/auth/quantity/session-life`; `dependency/mailer`.

### 17. A decision's reach is invisible; an answered sentence reads "nobody agreed" (restructure, reword)

What is wrong. `option.sets` holds addresses, and the link index does not count them. `ogy impact` of
`decision/trigger-computed` reaches only its own options; `impact` of the rule it sets is empty. 52 of 66 decisions look
isolated to every link walk. And an entry whose whole sentence the owner chose by answering reads
`status: nobody agreed: from your words` next to `Decided in: ... (in force, by you)`: 47 rules in ogy's kb.

Proposal. The keys of `sets` are links for impact, `show` and the area map. An entry settled by a person's answer reads
"chosen by you in <decision>". Whether the answer also counts as agreement is owner decision 8.

Cost. Small.

Web example. `ogy impact decision/lock-after-attempts` reaches the value, the case `lock` and the rule that reads it.

### 18. Evidence and proof work for Python only (move-to-YAML)

What is wrong. `code:` links must end in `.py` ("code: links to Python files only"); a proof must be
`<path>.py::<function>`. A web application in TypeScript can cite no code and prove nothing.

Proposal. `evidence:` in `ontology.yml` or `ogy.yml` lists schemes, file patterns and the proof pattern; the symbol
reader is chosen by file type, with "the file exists" as the weakest reader.

Cost. Medium (a symbol reader per language is shelf work); the declaration itself is small.

Web example. `src: code:web/src/auth/signIn.ts#signIn`; `proof: web/tests/signIn.test.ts::locks after five`.

### 19. Dead parts of the kind language (delete)

`one_part` and `moved_from` are implemented, linted and documented, and no kind uses them. Seven kinds carry `dropped`
or `renamed` lists from finished migrations (`rule: ["on"]`, `term: [of, distinct, example, borrowed, group]`,
`workflow: [trigger]`...). `STORED_STATE` bans 29 field names from past versions. Delete the two features; clear the
lists once the three knowledge bases are migrated; keep `STORED_STATE` only if it moves to YAML.

### 20. Texts that contradict the model (reword)

- Term `area`: "not a kind". It is a kind.
- Term `because`, term `proof`: findings 11 and 14.
- Rule `who-may-say-yes`: "a second human actor is a finding". Not implemented; `starts.yml` ships one human, the fixture two.
- README, "The software ontology": lists actor and rule under "Why".
- `kinds/guard.yml`: `on -> workflow` (broken, finding 3).
- Step and case guidance: silent on before or after (finding 10).

## 4. The target model

29 kinds (from 32): `heard`, `guard` and one of `view`/`command` go. Names in brackets are the renames of finding 16 and
wait for the owner.

```
every kind also takes (declared in ontology.yml): title, src, because->principle|decision|rule, by->>rule, proof, agreed

product and software:
  actor: !says !nature(human|ai|program)
  area: !says near->>area
  decision: !question context structure
    option: !says sets
    guess: !chose->option !why heard
    answer[]: !chose->option !said !at !where note delegated->decision
  entity: !says
    attr [attribute]: says !type(text|number|flag|money|date|time|duration) of->set|entity many max->value optional derived->>...
    state: !says
    transition: from->>state !to->state
  rule: !says reads->>value|set|config_key
  set [enum]: !says !members
  term: !word says names->any avoid            exactly one of says, names
  value [quantity]: !says !is !unit
  workflow: !says !start->step schedule->value event->transition for->capability
    end: !says !result(success|failure)
    step: says actor->actor calls->workflow shows->>entity|attr
      choice: !label when->>... !then->step|end|workflow
        effect[]: !do(create|delete|write|transition|tell) !on->transition|entity|attr|actor|external
      case: order when->>... ends->>end !then->step|end|workflow
        effect[]: as above
      timeout: !after->value !then->step|end|workflow
        effect[]: as above
product:
  goal: !says !for->>actor
  capability: !says !for->>goal
software:
  interface (was view, command): !says !serves->>step offers->>choice as
  operation: !says performs->>choice|case|timeout uses->>external
  external [dependency]: !says pin
    deviation: !when->>value|external !says
  config_key [setting]: !says !name binds->value|set
constitution/:
  principle: !says why

generic checks named in YAML: reachable, ends-reached, callee-ends-covered, choices-offered, started,
                              layer-direction (software may name product, never the reverse)
```

One home per question, after the changes:

| Question | Home |
|---|---|
| Why does the product exist | goal, `for` an actor |
| What can it do | capability, `for` a goal |
| How is one result reached | workflow, `for` a capability |
| Who may act here | the step's actor |
| Same actor, fewer choices | `choice.when` |
| The product refuses or branches | a case |
| What must stay true, testable | rule; holders name it with `by`; it `reads` its numbers |
| What was asked and chosen | decision; it may stand alone |
| A value judged against | principle; cited with `because` |
| A word | term; it `names` the entry that defines it, or says one line |
| How an actor reaches a step | interface |
| The code that changes things | operation |
| What we depend on | external; its surprises are deviations |

What moves from Python to YAML:

| To | What |
|---|---|
| `ontology.yml` | layer order and link direction; common fields; harm tags, their order and `alone`; evidence schemes, file patterns, proof pattern; reserved names; the name of the shared area; (optional) file layout per kind |
| `workflow.yml`, `decision.yml` | every Flow and Settling name written out |
| `step.yml` | the step shapes as `requires` |
| `term.yml`, `principle.yml` | the glossary and printed-first roles, the word limit |
| every kind | `sentence:` (which field is its sentence) |
| link fields | `hash: none|link|target` |
| enum members | `harm` |
| `starts.yml` and a block template | everything `init.py` writes by name |

Left in Python on purpose: the graph algorithms (reach, orphans, cover), the hashes, the review queue, the reply grammar,
moves and the ledgers. They are parameterised by names, never by the names themselves.

## 5. Decisions only the owner can make

Each has the recommendation first.

1. **May a decision stand alone, with no entry to set?**
   a. Yes: a decision whose outcome changes no entry is its own record; a rule is written only when a test could catch it
   broken. (recommended: 56 of 66 decisions exist with a mirror rule that says the option again)
   b. Yes, and the 60 mirror rules are also sorted now, each kept as a real rule or removed.
   c. No: every decision keeps setting an entry.

2. **Which kinds may be held to a rule with `by`?**
   a. Every kind; `by` is a common field like `because`. (recommended: today's list of 8 leaves out commands and
   operations, which is where ogy's own rules apply, so `by` is used 0 times)
   b. The 8 kinds, plus command, view, operation and capability.
   c. Keep the 8.

3. **Does the guard kind stay?**
   a. No: a refusal is a case that ends in failure; who may act is the step's actor. (recommended: one home per
   question; all 9 real guards sit on steps and read as cases)
   b. Keep it only for a software entry that refuses a product step; forbid it inside one layer.
   c. Keep it as it is, and fix `on -> workflow` in the flow check.

4. **Are view and command one kind?**
   a. One kind, `interface`, with an optional `as`. (recommended: no check tells them apart)
   b. One kind under another name (`surface`, `access`).
   c. Keep two.

5. **May a product entry link to a software entry?**
   a. Never; software names product. It is an error. (recommended: it is what the layer principle says; taskloop-fit
   has 35 such links in one workflow)
   b. Never for new links; existing ones are listed as work.
   c. Allowed; the layers are folders only.

6. **How do a term and the entry of the same name live together?**
   a. The term `names` the entry and has no sentence of its own. (recommended: one sentence per concept, and the
   glossary stays the one list an agent loads)
   b. No term for a word an entry defines; the glossary prints entities, actors and states beside the terms.
   c. Keep both sentences.

7. **Is who answered computed?**
   a. Yes: drop `answer.from` and `agreed.from`; an answer with `delegated` is an agent's. (recommended: the check
   already forces the two fields to agree)
   b. Keep `from` as the readable field and compute nothing.

8. **When the owner answers a decision, does that agree to the sentences the option sets?**
   a. Yes, when the card showed those sentences: they read "decided by you". (recommended: the owner chose that exact
   text; 47 rules read "nobody agreed" today)
   b. No, and the status says "chosen by you in <decision>", never "nobody agreed".
   c. Keep as it is.

9. **Which effects exist?**
   a. create, delete, write, transition, tell; `count` and `counter` go; an external is only told; `do` members carry
   harm. (recommended)
   b. The same, and `write` on an external stays.
   c. Keep the six.

10. **Do edges live only on rows?**
    a. Yes: drop `step.then`; every system step has cases. (recommended: effects always have a home; one shape fewer)
    b. No: let a step with a plain `then` hold effects.
    c. Keep both shapes.

11. **Is the why-chain one verb and required?**
    a. `for` on workflow, capability and goal; required on capability and goal; an unbuilt capability is work left.
    (recommended)
    b. One verb, nothing required.
    c. Keep realizes, serves and for.

12. **Does a step say what it shows?**
    a. Yes, `step.shows` links to entities and attributes. (recommended: reads are most of a web application and are
    outside the graph today)
    b. Put it on the interface, in the software layer.
    c. Not yet: prove it on one real page first (decision smaller-next-step).

13. **Which renames?**
    a. `config_key` to `setting` and `external` to `dependency` only. (recommended: the two that remove real confusion)
    b. Those and `value` to `quantity`, `set` to `enum`, `attr` to `attribute`.
    c. None.

14. **How far does the move to YAML go now?**
    a. All of finding 4, with a second toy ontology as its test, before any kind change. (recommended: it makes every
    other item a YAML edit)
    b. Only what the kind changes above need (Flow and Settling names, common fields, harms).
    c. Later.

15. **Which kinds need a proof?**
    a. Rows, rule, operation, interface, config key, deviation, entity, value; not step. (recommended)
    b. Only rule and value, as the glossary says.
    c. Keep the 13.
