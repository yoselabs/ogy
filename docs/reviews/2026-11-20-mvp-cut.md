## The MVP

The MVP is the smallest set of work that lets each of these happen on task-loop's `land` area:

1. an agent captures the area (from code, docs and the owner's words) into `docs/kb` through ogy;
2. the owner reviews and agrees it in rounds (`ogy review` / `ogy reply`);
3. a later change to an entry shows up as work (`ogy work`, and "changed since you agreed" in review);
4. ogy's checks gate commits and lands in task-loop.

Verdicts:

- **done**: built, with a commit or file as evidence.
- **MVP**: needed for the four points above.
- **later**: not needed for them, with the reason.

A bead with sub-items is MVP when any sub-item is MVP. It is done only when every sub-item is done or dropped.

Sizes are in agent build time:

- **S**: under an hour.
- **M**: a few hours.
- **L**: a day or more.

The reconcile doc's own S, M and L (S = under a day) are not reused.

## Note on the any-gate dependency

`304dc07` and `28e2721` concern ogy's own repository: its pre-push gate runs `just kb` before shelf's any-gate until an
any-gate release lands. This does not touch task-loop, whose lands are gated by the factory's `just check`, so the MVP
does not wait on it.

## Biggest uncertainty

**How built lines are recorded (G1).** It decides whether "a change shows up as work" means anything on a KB captured
from working code. Should the agent stamp each entry after running its proof test, or should ogy run the proof? Should
code-sourced entries start as built? Mapping about 50 rows and rules to task-loop's `tests/steps/test_land*.py` also
sets most of P7's size.

The second risk is ontology churn. .76, .42 and the 60-rule sorting round all change kinds. Each change after the land
capture brings agreed entries back to the owner as "changed since you agreed", unless `ogy migrate` proves it a rename.
